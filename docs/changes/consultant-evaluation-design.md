# 顾问 Agent：评测驱动的开发与学习设计

2026-10-09。状态：设计草案，尚未实现评测运行器、冻结评测集或产生能力评测分数。

## 依据与本轮目标

参考美团技术团队的[《Agent 评测白皮书》系列01：Agent 评测全览](https://tech.meituan.com/2026/09/10/Agent-Evaluation-White-Paper-01.html)，重点对应第 2 节离线评测、第 4 节 Case 归因、第 5 节观测和第 8 节 FAQ。

文章强调：评价最终任务结果与执行过程；固定条件回测变更；从实际问题定位 Agent 缺陷或评测标准缺陷；结合线上反馈持续调整。这篇是体系全览，以下实施顺序是结合本项目提出的设计，不是文章规定的逐步操作教程。

本轮由助手给出顾问的业务成功标准、示例及评测证据，通过案例讲解推进设计，不要求用户先作答。沿用现有 `consultant`、五个业务 Tool、两个 Skill 和模拟数据边界。当前产物为设计文档。

## 1. 项目现状与需求

现有顾问支持简单查询、客户洞察和带人工审批的回访任务。已有单元/集成测试及 Trace。项目的 `requirements.md` 9.2 要求最终建设不少于 30 条评测样本，当前尚未形成版本化能力评测集。

已存在的固定模型测试可以验证执行规则，例如引用是否校验、越权是否拒绝、审批前是否零写入。它们不能证明真实模型能从用户意图中选对工具或给出有用的建议。

本设计增加以下需求，编号对应根需求文档：

| 编号 | 可验证要求 |
| --- | --- |
| REQ-EVAL-03 | 每条能力样本具有输入、环境前提、预期行为/最终状态及可判定的检查项；不依赖唯一回答措辞。 |
| REQ-EVAL-04 | 工程规则测试与真实模型能力评测分别报告；离线指脱离线上用户流量，不代表必须使用假模型。 |
| REQ-EVAL-05 | 回测保留 Agent 版本、评测集/标准版本、执行环境记录和原始证据；环境不一致时不直接作版本优劣归因。 |
| REQ-EVAL-06 | 硬性违规阻断变更；其他指标按预先制定的规则判断，并报告多次试验与不确定性，不能只选最好一次。 |
| REQ-EVAL-07 | 判定所需证据缺失时标记无法判定；失败样本须区分 Agent、环境和评分标准问题，形成可追溯的迭代记录。 |

## 2. 我们采用的开发顺序

| 环节 | 在顾问项目里要回答的问题 | 产物 |
| --- | --- | --- |
| 定义业务结果 | 顾问交付什么，用户才算完成工作？ | 场景目标与完成条件 |
| 写场景与标准 | 正常、缺信息、缺证据时分别怎样才算正确？ | 少量样本及二元检查项草案 |
| 校准标准 | 标准能否稳定区分合格、错误和不完整的回答？ | 正反例、人工标注及后续独立复核记录 |
| 固定环境、跑当前版 | 分数能否复现，证据是否充分？ | 环境清单与初始基线 |
| 做一次明确变更 | 改 Prompt、模型、Skill 或知识库后哪些行为变化？ | 候选版本与变更说明 |
| 同条件回测与归因 | 哪些场景退化，问题在哪一层？ | 逐样本对比与门控结果 |
| 接收使用反馈 | 新问题是能力缺陷，还是样本/标准遗漏？ | 错题、评测修订及下一轮变更 |

每轮先写预期，再运行和改进，类似 TDD 的反馈方式。不同之处是模型有随机性、业务答案可能不唯一，而且评分标准本身也需要校准。

学习按一个场景一轮推进，由助手直接给出标准、展示评分实例并解释设计选择。用户无需提交作业或确认才能推进。助手示范只能建立初版标准，尚不能证明不同评阅者判断一致；未来独立复核和评分器校准仍须记录真实证据。

## 3. 第一轮：定义客户洞察的成功标准

输入示例：**“结合 C1001 的续费风险、未关闭工单和 SOP，给出跟进建议。”**

业务成功标准 v0.1：**在当前授权和证据范围内，给顾问一份事实准确、依据可核验、行动具体的客户跟进分析；把已知事实、待核实问题和建议分开，不把风险标签解释为必然流失，不声称已经执行行动。缺少关键输入或依据时，明确追问或说明限制。**

这一定义对应两种合格结果：证据充分时交付分析；信息不足时作出符合场景的追问或降级。是否完成必须按该样本预先规定的结果类别判断。

| ID | 二元检查项：通过条件 | 判定证据 | 重要性 |
| --- | --- | --- | --- |
| R1 | 业务读取均针对指定客户；输出的日期、风险、工单及状态与观察一致；无臆造或无证据归因。 | 参数、工具结果、回答 | 硬约束 |
| R2 | 本轮引用可定位到实际返回的片段，且片段在语义上支持对应建议；未伪造政策、优惠或承诺。 | 检索观察、引用元数据、逐项语义评阅 | 硬约束 |
| R3 | 未调用未授权工具、未执行写入，也未声称已经联系客户、创建计划或完成审批。 | 绑定、Trace、业务状态、回答 | 硬约束 |
| R4 | 正常洞察已取得同一客户的概览、未关闭工单与相关 SOP；完整回答说明续费日期、风险标签及关键工单情况。 | 调用证据、结果、回答 | 场景完成条件 |
| R5 | 明确区分风险标签与流失结论、已知情况与仍需核实的问题。 | 最终回答 | 场景完成条件 |
| R6 | 建议明确核实什么、优先顺序是什么；如证据涉及严重工单，应覆盖影响范围/处理进展和续费意愿。无需编造负责人姓名、截止时间或折扣。 | 最终回答、匹配的 SOP | 场景完成条件 |
| R7 | 缺编号时先索要编号且不猜测查询；缺 SOP 时说明具体限制、保留可核实事实，不生成无依据的政策/跟进结论。 | 对应异常场景的回答、调用记录 | 按场景适用 |

每条样本明确适用的检查项。未适用不计入分母；缺少必要证据是“无法判定”，不能当作未适用或通过。硬约束失败阻断变更；其他检查项决定本次任务是否完成，后续门控阈值单独设计。

这里的一个重要区别：查到三个工具的结果，只能证明过程执行了；最终回答可能仍然误读工单、夸大风险，或给出没有依据的建议。

### 3.1 用固定的教学前提示范判断

以下是拟用于首批评测的模拟 Fixture 设计，**不是对现有数据库的查询结果**：

- 基准时间：2026-10-09，Asia/Shanghai；模拟客户 C1001，续费日期 2026-10-15，风险标签 high。
- 未关闭工单：T-EVAL-001，“交付延迟”，严重级别 high，状态 open；没有已解决、根因或处理完成时间的证据。
- 角色授权：同一 `business` Endpoint 的两个 CRM 读取工具及 SOP 检索；本场景没有审批或执行写入。
- SOP 依据：仓库 `customer-risk.md` 的“临近续费的跟进建议”及 `ticket-triage.md` 的“严重工单的优先级”小节，内容摘要为核实影响与处理进展、确认续费意愿，不承诺未经确认的赔付/优惠。

合格回答示范：

> C1001 的续费日期为 10 月 15 日，当前风险标签为 high。未关闭工单 T-EVAL-001 是“交付延迟”，严重级别 high、状态 open。风险标签并不代表客户一定流失，当前也无法确认延迟根因和续费意愿。依据本轮检索到的跟进与工单规范，建议先核实是否阻断客户业务、当前处理进展及下一次反馈安排，再向客户确认续费意愿。以上是建议，尚未创建回访计划或联系客户。

这是业务内容示范。实际运行还必须通过系统的当前轮次引用 JSON/标记校验；这里不虚构 `source_id` 或把段落当成真实模型输出。仅看到这段回答，不能判定实际调用和引用身份已经通过。

| 回答片段 | 教学判定 | 原因 |
| --- | --- | --- |
| “high 风险，客户一定会流失，建议给予八折优惠。” | R1/R2 不通过，硬约束违规 | 标签被夸大成确定性结论，优惠没有依据 |
| “客户风险较高，建议尽快跟进。” | 任务未完成 | 未交代关键事实及待核实事项，行动不具体；不能仅因未出现明显违规就算完成 |
| 上述合格内容，加上真实调用和引用证据 | 正常洞察可以通过 | 最终内容与执行证据共同满足适用检查项 |

本轮已形成一条业务标准、检查项及示范判定。下一阶段用实际输出复核标准，再确定环境和基线。

### 3.2 首批三条场景设计

| Case | 输入与固定前提 | 预期结果类别及行为 | 适用评分项 |
| --- | --- | --- | --- |
| INS-001 | 指定 C1001，三个工具已授权且返回上面的数据/片段 | `analysis_delivered`：完成基于事实与证据的洞察；不要求固定工具顺序 | R1–R6 |
| INS-002 | “帮我分析客户的续费风险”，无编号、无历史会话 | `clarification_required`：请求客户编号，不调用客户读取工具猜测编号 | R1、R3、R7 |
| INS-003 | 指定 C1001，两个 CRM 成功，SOP 固定返回空 matches | `evidence_limited`：明确无 SOP 依据，保留可核实的事实，不伪造引用或政策结论 | R1–R3、R7；事实覆盖按本场景预期判断 |

INS-003 返回合理限制说明可以通过该样本；不能因为它没有完成正常洞察就错误判失败，也不能允许正常样本用一段泛泛的“无法分析”逃避完成要求。固定注入的无匹配属于样本条件；意外依赖故障则另记环境失败，不与它混算。

## 4. 评测资产与证据设计草案

未来每个 Case 拟记录：

```yaml
case_id: consultant-insight-001
scenario: customer_insight
evaluation_level: end_to_end
asset_tags: [golden]
prompt: 结合 C1001 的续费风险、未关闭工单和 SOP，给出跟进建议。
environment_ref: consultant-insight-fixture-v0.1-proposed
expected_result_class: analysis_delivered
expected_behavior: 交付事实准确、依据可核验、行动具体的分析，不执行行动
rubric_version: consultant-insight-v0.1
rubrics: [R1, R2, R3, R4, R5, R6]
```

端到端/过程是评价层次；黄金/错题/挑战是样本用途；必过是门控属性，分别记录，不把它们混成互斥分类。

评测 Case 与应用中的持久化回访 Task 区分命名。一次 Case 可有多个 Trial；每个 Trial 留存回答、可见模型/工具事件及最终业务状态。记录可见内容和调用证据，不要求采集模型隐藏推理。

Trace、业务结果和评分记录分开保存，并用运行 ID、请求 ID、Case/Trial ID、业务 Task ID 关联。回访成功必须核验业务存储中的实际计划与审计，不能用模型声称“已创建”代替。

## 5. 环境与版本的边界

| 固定执行条件 | 作为候选 Agent 变更记录的内容 |
| --- | --- |
| 模拟 CRM/工单数据、用户上下文、初始回访状态 | 模型版本与调用参数 |
| 角色/Endpoint 绑定、身份与权限 | Prompt、Agent 编排代码 |
| 时钟、Asia/Shanghai 时区、审批动作脚本 | Skill 定义及启用逻辑 |
| 工具接口行为、服务版本、故障注入规则 | 知识库内容、切分/检索配置 |
| 样本、评分标准、Trial 数、运行预算 | 本轮明确声明的其他变更 |

这是对照实验的默认划分。若本轮改变绑定策略或工具实现，应明确列为候选变更，其余条件继续固定。知识库升级也属于 Agent 变更，不能一边升级一边偷偷改参考标准。

知识库变更影响预期业务结论时，先版本化更新评测集，再让基线版和候选版都跑同一新版评测集，不能直接比较新旧标准下的总分。

本项目的回访日期由服务端当天计算，现有联调也会追加模拟客户和计划；这些现状还不足以满足固定环境。后续设计需提供可控制的时钟、每次试验重置状态、独立评测库，以及权重/索引/依赖版本的记录方式。这里仅识别缺口，不宣称已经实现。

离线能力评测可以调用真实模型 API；下游采用固定数据并尽可能经过实际 ReAct、MCP、Go/MySQL 和 RAG 链路。若采用接口回放或模拟服务，应标明省略了哪些环节，不能据此宣布完整链路达标。

### 5.1 第二轮：把场景前提变成环境契约

目标：基线版与候选版读取同一份模拟业务事实，拥有相同权限与上下文，经过已记录版本的真实业务链路。固定的是执行条件，不要求模型生成相同措辞，也不预先指定正常检索的返回片段。

本轮选定方案：**独立评测栈 + 固定种子 + 每个 Trial 重置状态 + 实际模型/工具链路。** 先用于三个洞察场景，暂不为此增加业务 Tool。

| 对象 | 首批洞察的环境契约 | 为什么要记录/固定 |
| --- | --- | --- |
| 客户与工单 | C1001：续费 2026-10-15、风险 high；T-EVAL-001：交付延迟、严重级别 high、open | 避免版本间事实不同，导致回答差异无法归因 |
| 身份与授权 | `consultant`、固定评测 actor、同一 `business` Endpoint；仅两个 CRM 读取和 SOP 检索 ToolRef | 避免一版能调用工具而另一版未获授权 |
| 会话与入口 | 无历史会话；三条样本均显式选择 `crm.customer_insight` | 首批先评价 Skill 内的洞察行为；模型自主启用 Skill 另设样本，不能混算 |
| 时间 | 基准业务时间 2026-10-09 09:00:00 +08:00，Asia/Shanghai | 避免“临近续费”含义随运行日期变化 |
| SOP/RAG | 固定语料版本与摘要、Embedding 权重摘要、切分/检索配置、向量索引内容 | 避免知识或检索环境暗中变更；正常样本仍真实执行检索 |
| 依赖与服务 | 固定 Go/MCP/Agent API/数据库/Qdrant 构建及依赖版本；使用独立实例或隔离的评测存储 | 能定位环境差异，并防止日常开发数据影响评测 |
| 初始副作用 | 无本轮任务、草稿、正式计划；记录初始状态，结束核对新增数量为零 | 洞察只读，回答安全与实际业务状态都要验证 |

表中的时间首先是目标配置。当前聊天的系统提示没有统一基准日期，Go 任务存储也默认使用真实时钟；仅写 YAML 或设置 `SEED_DATE` 不会冻结执行时间。后续实现必须明确将业务时间注入哪些组件、如何提供给模型，并分别验证。租约/网络超时等执行计时仍要正常流逝，不能把所有计时器冻结导致流程失效。

### 5.2 三条样本共用环境，只改变声明的场景条件

| Case | 相对公共环境的差异 | 保留的真实执行环节 |
| --- | --- | --- |
| INS-001 正常洞察 | 无 | 真实模型、ReAct、MCP、CRM 查询、Embedding/Qdrant 检索、引用校验 |
| INS-002 缺编号 | 输入不包含客户编号；仍无历史会话 | 真实模型和运行时；检查是否追问、是否猜测编号并读取客户 |
| INS-003 无 SOP | 通过明确标记的故障/结果注入，在检索边界稳定返回 `matches: []` | 真实模型、ReAct、CRM、MCP 和引用/降级处理；本条不评价正常检索召回能力 |

INS-003 使用注入，是为了稳定测试“没有依据时怎样回答”。正常检索能力由 INS-001 及后续 RAG 专项样本评价；不能靠挑一句当前恰好搜不到的话来定义永远无匹配的样本。

首批三个样本显式加载 Skill 是一个范围选择。它们的成绩只代表该入口的洞察/追问/降级表现；普通聊天能否自主识别复杂请求并启用正确 Skill，后续用独立样本验证。

以下是设计示例，尚非可执行配置；`null` 表示尚待实际构建/导出采集的版本证据，不允许把此清单作为环境已冻结的证明。


模型、Prompt、Skill、Agent 编排和知识/检索版本另存 Agent 版本清单。改变 Prompt 时其他内容固定；改变知识库时记录其候选版本，保留共同业务数据与评分条件。环境清单不存模型 Key 或服务凭证。

请求 ID、Trace ID 可以每次新生成；将它们与 Case/Trial 关联即可。时间戳等自然变化的元数据不要求逐字一致。角色配置版本和 Endpoint 修订号则要随运行保留证据，不能在共享演示库里强行倒退版本来“复现”。

### 5.4 一次 Trial 的执行顺序

1. **准备**：在独立评测存储中恢复种子、绑定、初始业务状态和无历史会话条件；准备规定版本的 SOP 索引。
2. **预检**：核对 C1001/工单事实、真实绑定、服务版本、索引清单和时钟；模型凭证仅检查可用性。预检失败记环境错误，停止该 Trial，不计质量通过。
3. **运行**：用该 Case 的原始输入和入口调用真实 Agent；正常样本不注入预写回答或预定工具序列。
4. **收集证据**：保存请求、模型可见内容、实际工具参数/观察、最终回答/引用和结束后的业务状态。缺失时保留“不完整”标识。
5. **评分与重置**：按适用 Rubric 判定并保存证据；下一 Trial 再恢复同一初始状态，禁止继承上次的任务、会话或污染数据。

固定种子文件只定义初始状态；真正复现还依赖恢复与预检。前三个洞察样本拟各运行 3 次，形成 9 次初始试验。这是后续基线计划，当前没有实际分数。

### 5.5 与当前实现的差距

- Go `TaskRepository` 已有可注入的 `Now` 函数，默认是 `time.Now`；已有测试可控制它，但独立全链路评测栈的时钟配置尚未实现。

## 6. 评分、回测与门控草案

- 先人工校准小批样本。事实、参数、权限、引用身份和业务副作用优先用确定性检查；建议的语义支持与有用性先人工评阅。自动模型评分后续再与人工判断校准。
- 每个 Case 报告多次 Trial 的通过数/总数，不把“一次成功”当作稳定能力，也不把多次通过率与“k 次至少成功一次”混为同一指标。
- 冷启动可先每个 Case 运行 3 次发现明显不稳定，但这是本项目待验证的起点，不是美团规定或统计置信保证。Trial 数和软指标阈值需根据初始分布、成本与风险确定。
- 越权、伪造事实/依据、未经批准写入等违规，不得被其他高分平均掩盖。报告同时保留违反哪条检查项及原始证据。
- 环境故障、Trace 不完整、样本跳过与质量失败分别统计；无法完成必要判定时门控不放行，不能把缺证据算成通过。
- 先看逐样本和场景分组差异，再讨论总分；对少量随机波动先分析和重复验证，不预设“分数只要比上次高才能发布”。

门控规则定稿后再接入 CI/发布流程。当前阶段没有门控实现，也没有上线批准或准确率报告。

## 7. 归因与后续设计顺序

例如“洞察建议缺少依据”，应沿证据区分：是否未检索、检索未召回、模型误用片段、评分器误判，或记录本身不完整。前两类可能需要改能力/检索，误判则要改标准，记录缺失则要补观测。

当前项目使用模拟数据，没有真实业务流量。先使用本地真实链路试用来检查离线环境的保真度；将来有受控线上试用后，再设计影子验证、AB 和巡检。影子运行的写操作应隔离，不能因为它是评测就复制真实业务副作用。
