# MCP Endpoint 分类与角色绑定：需求草案

> 历史规格：已由 [角色 Endpoint 修正](role-endpoints.md) 替代其中的领域分类与跨角色复用关系。现行 Endpoint 按角色归属，领域仅分类内部工具。以下文字保留当时设计背景，不是当前验收依据。

日期：2026-10-08。状态：用户已确认并授权实施；需求依据保留。对应 [技术设计](mcp-endpoints-design.md) 与 [实施验证](mcp-endpoints-tasks.md)。

## 1. 目标与术语

作为本地管理员，我希望先管理可连接的 MCP 服务及分类，再给不同角色选择服务和其中的工具，使各类 Agent 的连接来源和能力边界可独立配置、复用。

- Endpoint：一个独立的 MCP 服务连接，不是单个 Tool，也不是聊天意图路由。
- Endpoint 分类：管理员维护的展示分类，例如 CRM、MES、综合业务；不自动授予权限。
- Tool 领域：工具自身的业务域。综合 Endpoint 可以同时提供 CRM、MES 等多个领域的工具。
- 角色连接绑定：管理员明确允许某个角色使用的 Endpoint 集合。
- 角色工具绑定：在该角色允许连接的 Endpoint 内，进一步勾选可用工具。

支持一个角色绑定多个 Endpoint、一个 Endpoint 被多个角色复用；不强制“一角色一个 Endpoint”，也不自动绑定 Endpoint 内全部工具。此关系已随本需求确认。

## 2. 用户故事与可测试验收标准

### REQ-ENDPOINT-01：管理连接与分类

作为管理员，我能在现有前端管理区域查看、添加、修改和停用 MCP Endpoint，按分类与名称搜索。

1. 当管理员查看连接列表时，系统应显示稳定标识、名称、分类、连接地址、启用状态和最近一次连接检查结果。
2. 当管理员修改名称或分类时，系统应保留该 Endpoint 已有绑定关系；分类修改不改变授权。
3. 当管理员保存无效地址、重复标识或不符合安全限制的地址时，系统应拒绝保存并显示明确原因。
4. 第一版应支持现有 Streamable HTTP 连接；不扩展到远程进程启动或任意 Shell/stdio 命令。

### REQ-ENDPOINT-02：实际发现每个服务的工具

作为管理员，我能检查指定 Endpoint 的连接，并查看它实际提供的工具。

1. 当连接检查成功时，系统应展示该服务实际发现的工具、说明、参数 Schema、领域与可绑定状态。
2. 当连接超时、认证失败或工具契约不兼容时，系统应明确展示错误，不得把失败标为成功。
3. 当不同 Endpoint 提供同名工具时，系统应按“Endpoint + 工具名”区分，不得合并或覆盖。
4. 连接检查应为非写入探测，不执行业务 Tool，也不调用模型。

### REQ-ENDPOINT-03：给角色绑定连接，再绑定工具

作为管理员，我能为不同角色分别选择 Endpoint，并只从其已选 Endpoint 的工具目录中绑定工具。

1. 当管理员编辑角色时，系统应展示其 Endpoint 集合和每个工具所属的 Endpoint。
2. 当管理员保存绑定时，系统应拒绝未授权 Endpoint 下的工具；空 Endpoint 集合和空工具集合均有效。
3. 当管理员移除某个角色的 Endpoint 时，系统应明确提示受影响的工具，并在确认保存时一并移除相应工具授权。
4. 新 Endpoint、新工具或分类变化不得自动扩大任何角色的权限。
5. 绑定应持久化，并防止并发编辑静默覆盖；保存失败时不得展示成功状态。
6. 本需求不增加用户登录或角色创建系统；对已有及之后新增的角色采用一致的连接绑定能力。

### REQ-ENDPOINT-04：统一 ReAct 使用角色允许的连接

作为聊天用户，我使用当前角色的工具，而不能通过 Prompt 指定任意连接或绕过绑定。

1. 当 Agent 准备工具集合时，系统应仅暴露来自当前角色已绑定、启用且契约兼容 Endpoint 的已授权工具。
2. 当模型请求调用工具时，系统应根据管理员保存的工具来源找到对应 Endpoint，不接受模型提交的 URL、连接凭据或替代来源。
3. 同名工具来自多个 Endpoint 时，Agent 应能区分来源；实际调用结果和审计应保留其来源，且调用到正确服务。
4. Endpoint 分类不得用于按用户意图预选工具；所有聊天继续使用统一 ReAct，允许零次、一次或多次工具调用。
5. 当角色没有可用工具时，Agent 仍应能够回应问候和说明能力限制；不得伪造业务结果。

### REQ-ENDPOINT-05：服务端再次授权与实时撤权

作为项目维护者，我希望连接隔离不能只依赖界面或模型。

1. 每次调用前，Agent API 和本项目管理的 MCP Server 应独立校验角色、Endpoint 来源、工具授权、配置版本、参数与风险。
2. 当连接被停用、角色解绑连接或解绑工具后，新的调用及已开始循环中的后续调用应拒绝旧授权。
3. 当某个已绑定 Endpoint 不可用时，系统不得改用未绑定 Endpoint、旧授权或另一服务的同名工具来完成调用；依赖该来源的业务请求应明确报告失败。
4. 即使已绑定 Endpoint 和写工具，没有人工确认也不得执行写入。
5. 第一版只承诺对本项目管理的 MCP Server 进行完整双侧校验；不得声称任意第三方服务已具备相同安全协议。

### REQ-ENDPOINT-06：连接安全与凭据保护

作为维护者，我希望管理连接不会引入任意网络访问和密钥泄露。

1. 首版连接目标应限定在运维预先允许的本地开发或项目容器地址范围；前端管理员不能修改该安全范围。
2. 非 HTTP(S)、带内嵌用户名或密码、云元数据等未授权目标应被拒绝；不得通过重定向绕过连接范围限制。
3. 认证密钥应仅通过服务端环境变量读取。管理页只保存或显示凭据引用，不接受、返回或展示明文密钥。
4. 日志和错误不得包含凭据、签名头或含敏感参数的原始连接地址。
5. 管理入口保持当前本地开发限制；Endpoint 注册及绑定接口不得作为模型 Tool 暴露。

### REQ-ENDPOINT-07：兼容现有配置与可追溯验证

作为现有项目使用者，我希望更新后人工配置不会丢失。

1. 初次升级应把当前单一 MCP 连接作为默认 Endpoint，保留已有角色的工具选择；重复启动不覆盖人工配置。
2. Endpoint 和绑定变化应记录修改对象、修改前后配置、版本及请求标识，但不得记录密钥。
3. 测试应至少覆盖两角色使用不同 Endpoint、同名工具来源隔离、Endpoint 停用、循环中撤权、连接失败、非法地址、并发保存及旧配置迁移。
4. 真实联调只使用项目模拟数据；未执行的验证不得标为通过。

## 3. 范围与非目标

- 延续当前五个业务 Tool，不因连接管理扩展业务能力。
- 复用现有前后端及 MySQL，不新增管理服务进程、消息队列或服务发现平台。
- 分类与业务模块分拆是不同问题：本需求不强制将现有 MCP 的每个领域拆成独立部署。
- 不引入任意公共 MCP 市场接入、OAuth、生产多租户鉴权、自动故障切换或模型自主连接服务。
- 此阶段不编写业务代码、数据模型、API 协议或实施任务；确认需求后进入设计阶段。
